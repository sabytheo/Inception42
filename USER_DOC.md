# User documentation

This document is meant for an end user or an administrator of the Inception
stack. It explains what the stack provides, how to start and stop it, how to
reach the website and its administration panel, where the credentials live, and
how to verify that everything is running correctly.

If you are looking for how to set the project up from scratch or how it is
built internally, read [`DEV_DOC.md`](DEV_DOC.md) instead.

---

## 1. What the stack provides

Inception runs a self-hosted **WordPress website served over HTTPS**. Three
services cooperate to deliver it, each in its own container:

| Container   | What it does                                                                                   | Reachable from                       |
|-------------|------------------------------------------------------------------------------------------------|--------------------------------------|
| `nginx`     | Terminates TLS and serves the site. It is the **only** way into the infrastructure.             | The host and the network, port `443` |
| `wordpress` | Runs WordPress and PHP-FPM. Generates every dynamic page.                                       | Only the other containers            |
| `mariadb`   | Stores all the site's data: posts, pages, users, settings.                                      | Only the other containers            |

Everything else is closed. There is no HTTP port, no exposed database port and
no SSH: the only door is `https://tsaby.42.fr` on port 443.

Two storage areas keep your data safe when containers are rebuilt or restarted:

* the **database**, stored on the host in `/home/tsaby/data/mariadb`
* the **website files** (WordPress core, themes, plugins, uploaded media),
  stored on the host in `/home/tsaby/data/wordpress`

## 2. Before the first start

Two things must be in place on the host machine.

**The domain name must resolve locally.** The site answers to `tsaby.42.fr`, not
to `localhost`. Add this line to `/etc/hosts` (requires `sudo`):

```
127.0.0.1	tsaby.42.fr
```

Check it with:

```bash
ping -c 1 tsaby.42.fr
```

**The credential files must exist.** They are intentionally not part of the Git
repository, so on a fresh clone you have to create them. See
[`DEV_DOC.md`](DEV_DOC.md) §2 for the exact list and contents.

## 3. Starting and stopping the project

All the commands are run from the root of the repository, using `make`.

### Start

```bash
make
```

This creates the host data directories, builds the three images if needed, and
starts the three containers in the background.

The very first start takes a few minutes: the Debian images are downloaded, the
packages are installed, MariaDB initialises its database and WordPress is
downloaded and installed. Later starts take only a few seconds, because both
initialisations detect existing data and skip themselves.

### Stop

```bash
make stop
```

The containers are stopped but kept. `make` starts them again exactly where they
were. **No data is lost.**

### Stop and remove the containers

```bash
make down
```

The containers and the network are removed. The volumes and the data in
`/home/tsaby/data` are **not** touched, so `make` rebuilds a working site with
all your content still there.

### Reset everything

```bash
make fclean
```

> **Warning — this destroys your data.** `make fclean` removes the containers,
> prunes the Docker images and volumes, and deletes `/home/tsaby/data`
> entirely. The database, every post, every uploaded file and every installed
> plugin are gone permanently. Use it only to start over from a blank slate.

`make re` runs `make fclean` followed by a full rebuild.

## 4. Accessing the website and the administration panel

### The website

Open a browser on the host and go to:

```
https://tsaby.42.fr
```

The certificate is **self-signed**, generated by the NGINX container at startup.
No public authority vouches for it, so the browser displays a warning
("Your connection is not private", "Potential security risk ahead", …). This is
expected for a local development stack. Click *Advanced* then *Continue to
tsaby.42.fr* to proceed.

Note that only `https://` works. There is no listener on port 80, so `http://`
will simply fail to connect — this is by design, the subject requires port 443
with TLSv1.2/1.3 to be the sole entry point.

### The administration panel

The WordPress dashboard is at:

```
https://tsaby.42.fr/wp-admin
```

Log in with the **administrator** account. Its username is the `WP_ADMIN_USER`
value in `srcs/.env` and its password is the content of
`secrets/credentials.txt` (see the next section).

From the dashboard you can write posts, change the theme, install plugins,
upload media and manage users, exactly as on any WordPress installation. Media
uploads up to **64 MB** are accepted; both NGINX and PHP are configured for that
limit.

### The two accounts

The stack creates two WordPress users on the first start:

| Account          | Role          | Username comes from      | Password comes from            |
|------------------|---------------|--------------------------|--------------------------------|
| Administrator    | `administrator` | `WP_ADMIN_USER` in `.env` | `secrets/credentials.txt`      |
| Secondary user   | `author`      | `WP_USER` in `.env`      | `secrets/wp_user_password.txt` |

The `author` account can write and publish its own posts but cannot change the
site settings, install plugins or manage other users. Use it to check what a
non-administrator sees.

## 5. Locating and managing credentials

### Where they live

Nothing sensitive is stored in the Git repository. Credentials are split into
two places on the host, both listed in `.gitignore`:

```
Inception42/
├── secrets/                       # passwords — one per file, nothing else
│   ├── credentials.txt            # WordPress administrator password
│   ├── db_password.txt            # MariaDB application user password
│   ├── db_root_password.txt       # MariaDB root password
│   └── wp_user_password.txt       # WordPress secondary user password
└── srcs/
    └── .env                       # non-secret settings: domain, usernames, e-mails
```

The files in `secrets/` are mounted read-only by Docker into the containers at
`/run/secrets/<name>`, and read by the startup scripts. They are never copied
into an image and never appear in a container's environment.

### Protecting them

Restrict them to your own user:

```bash
chmod 600 secrets/*.txt srcs/.env
```

Never commit these files, never paste their contents into a chat or an issue,
and never add them to an archive you share. A credential found in the Git
repository fails the project outright.

### Changing a password

**WordPress passwords** are stored in the database once the site is installed,
so changing the file after the first start has no effect. Change them from the
dashboard instead: *Users → All Users →* pick the account *→ Set New Password*.
Update the corresponding file in `secrets/` afterwards so both stay in sync.

**Database passwords** are set when MariaDB initialises. Changing
`db_password.txt` or `db_root_password.txt` afterwards will not update the
running database — the containers would then fail to connect. To change them
cleanly you need either to alter the users inside MariaDB by hand, or to reset
the stack with `make fclean` (which destroys all data) and start again.

## 6. Checking that the services are running correctly

### All three containers are up

```bash
docker ps
```

You should see exactly three containers named `nginx`, `wordpress` and
`mariadb`, all with a status of `Up`. A container that keeps reappearing with a
short uptime is crash-looping — its logs will say why.

### Only port 443 is published

```bash
docker ps --format '{{.Names}}\t{{.Ports}}'
```

Only the `nginx` line should mention a host port, and it should be
`0.0.0.0:443->443/tcp`. Neither `wordpress` nor `mariadb` should publish
anything.

### The site answers over HTTPS

```bash
curl -kI https://tsaby.42.fr
```

`-k` accepts the self-signed certificate. A `HTTP/1.1 200 OK` means NGINX,
PHP-FPM and MariaDB are all working together — the page could not be generated
otherwise.

### The TLS version is correct

```bash
curl -kIv --tlsv1.2 --tls-max 1.2 https://tsaby.42.fr   # must succeed
curl -kIv --tlsv1.1 --tls-max 1.1 https://tsaby.42.fr   # must fail
```

Only TLSv1.2 and TLSv1.3 are accepted; anything older is refused by design.

### The database is answering

```bash
docker exec -it mariadb mariadb -u root -p -e "SHOW DATABASES;"
```

Enter the content of `secrets/db_root_password.txt` at the prompt. The WordPress
database (the `MYSQL_DATABASE` value from `.env`) must be listed.

### The two WordPress users exist

```bash
docker exec -it wordpress wp user list --allow-root --path=/var/www/wordpress
```

Two accounts must be listed: the administrator and the `author`.

### Reading the logs

```bash
docker logs nginx          # access and error logs of the web server
docker logs wordpress      # PHP-FPM and the installation script
docker logs mariadb        # database startup and errors
docker logs -f nginx       # follow live
```

This is the first place to look whenever something does not behave as expected.

### Data really persists

```bash
docker exec -it wordpress ls /var/www/wordpress
ls /home/tsaby/data/wordpress
ls /home/tsaby/data/mariadb
```

The first two listings show the same WordPress files, seen from inside the
container and from the host. To prove persistence end to end: publish a post,
run `make down`, then `make` again — the post is still there.

## 7. Common problems

| Symptom                                        | Likely cause and fix                                                                                          |
|------------------------------------------------|---------------------------------------------------------------------------------------------------------------|
| The browser cannot find `tsaby.42.fr`          | The `/etc/hosts` entry is missing. See §2.                                                                     |
| "Your connection is not private" warning        | Normal — the certificate is self-signed. Accept it and continue.                                               |
| `http://tsaby.42.fr` does not connect           | Expected. Only HTTPS on port 443 is served. Use `https://`.                                                    |
| `502 Bad Gateway`                               | The `wordpress` container is not ready or has crashed. Check `docker logs wordpress`.                          |
| The site hangs on the first start               | WordPress is waiting for MariaDB to finish initialising. Give it a couple of minutes and watch the logs.       |
| `Error establishing a database connection`      | `db_password.txt` no longer matches the password stored in MariaDB. See §5.                                    |
| A container restarts endlessly                  | Read its logs — usually a missing secret file or a malformed `.env`.                                           |
| `port is already allocated` on start            | Something else on the host is using port 443. Find it with `sudo ss -tlnp` and stop it.                        |
| An upload larger than 64 MB is rejected         | That is the configured limit, set in both `nginx.conf` and `www.conf`.                                         |
